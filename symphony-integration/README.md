# symphony-integration

Wires the real [openai/symphony](https://github.com/openai/symphony) (Elixir
reference implementation) to this repo's 150 Flue agents, using Symphony's
existing Linear adapter plus one new provider-native tool.

## What's actually in here

| File | What it is |
|---|---|
| `linear/agent_tool.ex` | A fork of Symphony's real `elixir/lib/symphony_elixir/linear/agent_tool.ex`, verified to compile against the actual upstream source (syntax-checked with `elixirc` against a clone of the repo). Adds one tool, `delegate_to_flue_agent`, alongside the existing `linear_graphql` tool. Every other line is byte-for-byte upstream. |
| `WORKFLOW.flue.md` | A **separate**, triage-only Symphony workflow (not a replacement for upstream's real `elixir/WORKFLOW.md` — see below). `tracker.kind: linear`, plus a prompt that tells the intake agent to call the new tool instead of doing the work itself. |
| `../role-label-map.json` | The deterministic routing table: Linear label → Flue role id. Generated by `scripts/generate-agents.mjs` (run via `./skills.sh generate`) directly from `roles.json` — not hand-maintained, so it can't drift. |
| `../server/dispatch.mjs` | A plain-Node HTTP bridge. Resolves the label and, if it matches, spawns `scripts/run-agent.mjs` under `npx tsx` as a subprocess to do the actual TypeScript/agent work — see "Why a subprocess" below. |
| `../scripts/run-agent.mjs` | Runs one Flue agent for one issue. Executed via `tsx`, not plain `node`, because `registry.ts` imports `agents/*.ts` with explicit `.ts` extensions and a `with { type: 'skill' }` import attribute that plain Node can't resolve. |

## Why this shape, not something fancier

Symphony's actual architecture (confirmed by reading `SPEC.md` and the
Elixir source, not assumed) rules out a few tempting designs:

- **No per-role Symphony instances.** Possible, but Symphony binds one
  adapter's entire `agent_tool_specs()` to one session (`Tracker.bind_agent_tools/0`,
  SPEC.md §10.5: *"Tool specs, adapter selection, and effective tracker
  settings MUST be bound to one session snapshot"*). Running 150 (or even 20)
  long-lived Elixir processes just to get 150 personas is real infra weight
  for what's actually a routing problem, not a concurrency problem.
- **No LLM-guessed role selection.** The prompt in `WORKFLOW.flue.md` doesn't ask
  the Codex intake agent to *infer* which specialist this issue needs from
  its title/description — that's exactly the kind of judgment call your own
  governance model (in the original flue-agent-org doc) says shouldn't be
  made silently. Routing is a deterministic label lookup
  (`role-label-map.json`), done in plain Node code in `dispatch.mjs`, not a
  model call. If routing is ambiguous or missing, the workflow is told to
  stop and ask a human for the label — never to guess.
- **A new tool, not a hijacked existing one.** `linear_graphql` is a raw
  passthrough Symphony ships for reading/writing Linear directly; overloading
  it to also mean "run a Flue agent" would be surprising and untestable in
  isolation. A second tool with its own name, schema, and error surface
  keeps the two concerns separate — this mirrors how Symphony itself keeps
  each tracker's tools (`jira`, `github`, `asana`, ...) as separate modules
  rather than one grab-bag tool.

## Why a subprocess, not a direct import

The first version of `dispatch.mjs` called `import(".../registry.ts")`
directly from plain Node. That breaks immediately: `registry.ts` imports
each `agents/<area>/<role>.ts` file with an explicit `.ts` extension, and
each of those imports its `SKILL.md` with `with { type: 'skill' }` — a
custom import attribute only `@flue/runtime`'s own loader understands.
Plain Node (even with `--experimental-strip-types`) can't resolve either.

Fix: `dispatch.mjs` never imports TypeScript at all. It resolves the label
(pure JSON, no TS involved), then spawns `scripts/run-agent.mjs` as a
subprocess via `npx tsx` — tsx can load real TypeScript. That subprocess is
also where the **unverified** part of this integration lives: `entry.agent.init()`
→ `harness.session()` → `session.prompt()` is a guess at `@flue/runtime`'s
actual public API, based only on the `createAgent()` shape used in the
generator. It has not been run against a real `@flue/runtime` package.
Isolating it in a subprocess means a wrong guess there fails loudly and
specifically (`agent_run_failed`, with the guess called out in the error
message) without taking down the HTTP server, and it's a small, obvious
place to fix once you've read that package's real exports.

## How a turn actually flows

1. Symphony polls Linear (its own existing adapter — nothing changed there),
   finds an issue assigned to the bot user in an active state, and starts a
   Codex turn using `WORKFLOW.flue.md`'s prompt, per SPEC.md §10.2.
2. The rendered prompt sees `{{ issue.labels }}`. If one starts with `role/`,
   Codex calls `delegate_to_flue_agent`.
3. `execute_delegate_to_flue_agent/2` (the new code in `agent_tool.ex`) pulls
   the *actual* normalized `issue` struct out of `opts` — this is not
   invented; SPEC.md §10.5 requires Symphony to pass the current issue as
   tool-execution context, and the real `codex/app_server.ex` does exactly
   that (`DynamicTool.execute(tool, arguments, dynamic_tool_binding, issue: issue)`).
4. It POSTs `{issue: {identifier, title, description, url, labels}}` to
   `http://127.0.0.1:4001/dispatch` (configurable via
   `Application.put_env(:symphony_elixir, :flue_dispatch_url, ...)` — note
   the port: 4001, not 4000, deliberately; see the comment in `dispatch.mjs`).
5. `dispatch.mjs` looks up the first `role/*` label in `role-label-map.json`,
   fails loudly (`422 ambiguous_role_labels` / `422 no_role_label`) rather
   than picking one if it's not exactly one match, then spawns
   `scripts/run-agent.mjs` under `npx tsx`, which calls
   `registry.getAgentByRoleId(roleId)` and runs that Flue agent's session
   against the issue text.
6. The result flows back through the tool call to the Codex turn, which
   (per the prompt) posts it as a Linear comment via `linear_graphql` and
   moves the issue state — or leaves a `needs-human` label if the
   specialist's own confidence check didn't clear.

## Setup

```bash
# 1. flue-agent-org side
cd flue-agent-org
npm install @flue/runtime
npm install -D tsx                  # run-agent.mjs's real TS loader
./skills.sh generate                # if you haven't already
node server/dispatch.mjs &          # loopback only, port 4001 by default

# 2. Symphony side (real clone, not this repo)
git clone https://github.com/openai/symphony.git
cp path/to/flue-agent-org/symphony-integration/linear/agent_tool.ex \
   symphony/elixir/lib/symphony_elixir/linear/agent_tool.ex
# Do NOT overwrite symphony/elixir/WORKFLOW.md — that's upstream's real
# production workflow. Run this as a second, separate symphony process
# (own project/label scope) pointed at WORKFLOW.flue.md instead:
cp path/to/flue-agent-org/symphony-integration/WORKFLOW.flue.md \
   symphony/elixir/WORKFLOW.flue.md
cd symphony/elixir
export LINEAR_API_KEY=...
export LINEAR_PROJECT_SLUG=...
export LINEAR_ASSIGNEE=...          # Symphony's bot user id
mix deps.get
./bin/symphony WORKFLOW.flue.md     # or: mix run --no-halt, pointed at this file
```

## What I did not build

- **Linear labels don't create themselves.** Someone (a human, or your
  `Product_Manager_Agent` at Tier 0 with a `linear_graphql` call of its own)
  still has to put a `role/frontend-developer`-style label on an issue in
  the first place. This integration starts *after* that label exists.
- **`agent.init()` / `harness.session()` / `session.prompt()` in
  `run-agent.mjs` is an unverified guess** at `@flue/runtime`'s real API —
  flagged inline in that file. If a Flue agent throws, the bridge returns
  `502 agent_run_failed` with the raw error and a hint pointing at that
  guess — it doesn't retry or queue; Symphony's own retry/backoff (SPEC.md
  §8.4) covers that at the turn level.
- **No auth on the dispatch bridge.** It binds `127.0.0.1` only and trusts
  whatever's on that box. Fine for one Symphony instance and one
  flue-agent-org instance on the same host; not fine to expose past that
  without adding real auth.
